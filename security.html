F.A.S. Security Overview

Forensic Auditing Services — Security & Compliance

ALS Consulting | Last updated: August 12, 2026

1

Encryption

Data at Rest

  • AES-256 encryption — All candidate data, audit logs, and compliance records encrypted at rest on Supabase (PostgreSQL)
  • Candidate identifiers hashed before storage — names and other direct identifiers are not stored in plaintext
  • Database backups encrypted with the same AES-256 standard

Data in Transit

  • TLS 1.3 — All API calls, webhook payloads, and client-server communication encrypted in transit
  • Enforced HTTPS across all endpoints (Supabase, Netlify)
  • No fallback to HTTP; mixed-content requests blocked
What We Don't Claim: We do not offer end-to-end encryption or zero-knowledge architecture. F.A.S. operates on a verified trust model where authorized compliance officers review candidate data — this by design requires decryption at the application layer for human analysis.
2

Authentication & Access Control

Roles

  • Supabase Auth — organization data is scoped by customer via Row Level Security; reviewer accounts are isolated per organization
  • Role types currently in use:
    • Admin
    • Compliance Officer
    • Senior Reviewer
    • Viewer
  • All access attempts logged with timestamp, user, and action taken
What We Don't Yet Formalize: A dual-authorization requirement for configuration changes and scoped elevation for executive-level views are on our roadmap but not yet built or enforced — we're not claiming either as a current control.

Multi-Factor Authentication (MFA)

Status: Supabase Auth supports MFA. Current default deployments use password + session-based authentication; MFA enablement is available on request.
3

Data Handling & Retention

Anonymization & Hashing

  • Candidate identifiers hashed before storage — direct identifiers are not stored in plaintext
  • Audit reports display candidate reference numbers, not names (configurable by client preference)

Retention & Deletion

  • 4-year baseline retention — matches the sourced policy in privacy.html (anchored to California FEHA's 4-year requirement, the current highest binding minimum across our covered jurisdictions)
  • Legal holds respected indefinitely
  • Clients can request manual deletion at any time (subject to legal requirements)

GDPR & International Compliance

  • GDPR Article 6 (Lawful Basis): Processing is legitimate interest + contract
  • GDPR Article 21 (Right to Object): Candidates can request exclusion from future audits
  • DPA available for enterprise customers

Audit Trail & Chain of Custody

  • All audit decisions logged with timestamp, user, and reasoning
  • Offline encrypted backups maintained for regulatory audits (see Infrastructure, below)

Infrastructure Security

Anthropic (Claude API): planned, not yet deployed — see the full disclosure on subprocessors.html. It is not part of the live architecture table above because it is not currently processing any data.

Database & API Security

  • No direct public database access — access governed by Supabase Row Level Security policies, scoped per customer
  • Webhook endpoint validation: API key resolved server-side against the customer record before any write is accepted
  • SQL injection protection via parameterized queries
Updated 2026-08-12: HMAC payload signature verification and rate limiting are now live on the candidate intake webhook — every request requires a per-customer signed payload (HMAC-SHA256, 5-minute replay window, constant-time comparison) on top of API-key authentication, plus a 60 req/min per-customer rate limit. Full-schema Row Level Security has also been re-verified: all client-data tables confirmed RLS-enabled with active policies, not just spot-checked.

Offline Backups & Chain of Custody

Offline Backup: ALS Consulting maintains AES-256 encrypted local backups of audit trails and decision logs at our Winston-Salem, NC facility, per subprocessors.html's subprocessor table. Provides physical custody for chain-of-custody requirements and disaster recovery independent of cloud providers. Retrieval requires dual authorization.

Development Process & Code Review

How F.A.S. Is Built

  • Developed by a solo founder using AI-assisted development (Claude Code), with every change reviewed and approved by the founder before it ships
  • No separate engineering team and no independent peer review process exists at present
  • Every AI-assisted change to source code, database schema, or deploy configuration requires explicit founder confirmation before being applied — a standing operating rule, not ad hoc

Verified Controls

  • Row Level Security confirmed enabled with active policies across the full schema, tested via live cross-tenant impersonation — not just checking policies exist on paper
  • Candidate identifiers HMAC-SHA256 hashed before storage, confirmed via direct code read
  • Zero confirmed exposure to automated secret-file probing (.env, .git/config, WordPress paths) — real 30-day traffic analysis, all attempts returned 404
What We Don't Yet Formalize: There is no dedicated written SDLC document beyond an internal pre-deploy checklist, no staging environment separate from production, and no independent third-party code review.

Pre-Deploy Practice

Changes to authentication, authorization, or data-access logic are tested against live cross-tenant scenarios before and after deployment, not assumed correct from reading the code alone. Schema and edge-function changes are version-controlled in git.

Incident Response

Detection & Containment

  • Continuous monitoring: Supabase configured with real-time alerts
  • Incident classification: Low / Medium / High
  • High-severity containment: Isolate systems, preserve logs, revoke credentials, block endpoints

Notification Protocol

  • 72-hour breach notification to affected organizations
  • Notification to designated security contacts via email
  • Law enforcement notification coordinated with customers' legal teams

Remediation & Recovery

  • Full forensic review post-incident
