📖 Overview
How this integration works, in one paragraph

Your ATS sends an HTTP POST to F.A.S.'s webhook endpoint every time a candidate is hired, rejected, or left pending on a job. F.A.S. validates the request, resolves your organization from your API key (never from anything in the request body), runs a deterministic (non-AI) check for a couple of common bias-proxy patterns in the rejection reason, and stores the event. No changes to your ATS's own code are required beyond adding this one outbound webhook call.

Endpoint: POST https://znjvjofsfvxccmidfpgy.supabase.co/functions/v1/candidate-event-intake
🔑 Authentication
Every request must include your API key
Authorization: Bearer <your-api-key>
  • Your API key is issued directly by ALS Consulting during onboarding — there is no self-service signup or key-generation UI. Contact your F.A.S. point of contact to receive it.
  • The key identifies your organization server-side. You never need to send your organization ID or name in the request — it's resolved from the key.
  • Missing or malformed Authorization header → 401.
  • A key that doesn't match any organization on file → 403.
✍️ Request Signing
Required as of 2026-08-12 — proves the request body wasn't tampered with or replayed

Separate from your API key (which proves you're a valid caller), every request must also be signed with a per-organization signing secret, issued alongside your API key during onboarding. This proves the specific payload is genuine and fresh.

X-Signature-256: <hex-encoded HMAC-SHA256>
X-Timestamp: <unix epoch seconds>
  • Signed value: {timestamp}.{raw request body} — the timestamp and the exact raw JSON body text (before any re-serialization), joined with a period.
  • Algorithm: HMAC-SHA256, hex-encoded, using your signing secret.
  • Timestamp tolerance: requests older than 5 minutes (or timestamped in the future) are rejected — this blocks a captured request from being replayed later, even with a technically-valid signature.
  • Missing either header, an invalid signature, or a stale timestamp → 401.
Example (Node.js): 
const crypto = require('crypto');
const timestamp = Math.floor(Date.now() / 1000).toString();
const rawBody = JSON.stringify(payload);
const signature = crypto
  .createHmac('sha256', YOUR_SIGNING_SECRET)
  .update(`${timestamp}.${rawBody}`)
  .digest('hex');
// send as X-Signature-256, with X-Timestamp: timestamp, and rawBody as the exact request body
⏱️ Rate Limiting
Added 2026-08-12
  • 60 requests per minute per organization (fixed 1-minute window).
  • Exceeding the limit → 429. Retry after the current minute window rolls over.
  • If your integration needs a higher sustained volume, contact your F.A.S. point of contact — the threshold is adjustable per organization.

🔍 Automatic Proxy-Flag Detection
Deterministic keyword matching — not AI, no LLM call

If rejection_reason_from_ats is provided, F.A.S. automatically checks it for two categories of language before storing the record:

  • employment_gap_flagged: true if the text contains any of gap, unemployed, inactivity, break in employment, resume hiatus.
  • keyword_mismatch_flagged: true if the text contains any of mismatch, missing core skills, insufficient keywords, fail qualification filter, mismatched criteria.
This is a first-pass heuristic, not a finished classifier — the keyword lists are a starting baseline, expected to be tuned against real rejection-reason text from your specific ATS over time. Don't treat either flag as a final determination; they surface records for human review in F.A.S.'s dashboard.

💻 Example Request

The signature must be computed over the exact raw body text you send — build the JSON string first, sign it, then send that same string as the request body (don't let your HTTP client re-serialize it separately).

BODY='{
    "candidate_id": "CAND-48213",
    "job_id": "REQ-1029",
    "job_title": "Senior Operations Manager",
    "outcome": "rejected",
    "rejection_reason_from_ats": "Candidate has a gap in employment history",
    "years_experience": 7,
    "protected_class_cohort": "protected_veteran",
    "demographic_source": "candidate_self_id",
    "occurred_at": "2026-07-22T14:30:00Z"
  }'
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "<your-signing-secret>" | sed 's/^.* //')

curl -X POST \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Content-Type: application/json" \
  -H "X-Signature-256: $SIG" \
  -H "X-Timestamp: $TS" \
  -d "$BODY" \
  https://znjvjofsfvxccmidfpgy.supabase.co/functions/v1/candidate-event-intake

⚠️ What's Not Built Yet
Don't assume these exist
  • No self-service signup. API keys are issued by ALS Consulting directly as part of onboarding.
  • No sandbox/test API key mechanism. There is currently no separate test environment distinct from your production key — coordinate directly with your F.A.S. contact before sending your first real events. Test with a few clearly-fake candidate IDs against your real key, and we'll clean them up together before you go live.
  • No idempotency/deduplication based on event_id or any other field — sending the same event twice creates two rows.
  • CORS is fully open (Access-Control-Allow-Origin: *) — this endpoint is designed for server-to-server calls from your ATS backend, not browser-side JavaScript. Authentication is enforced via the API key regardless of origin.
Questions? Contact your F.A.S. point of contact directly — there is no public support ticketing system for this integration yet.
